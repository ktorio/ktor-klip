# Summary

The core idea is to encode more information in auth schemes at the type level —
principal type, role model, anonymous fallback — so the compiler enforces
correctness across the entire auth pipeline, not just at the point of
`call.principal<T>()`.

The API lives in `ktor-server-auth` (JWT examples in `ktor-server-auth-jwt`). It is marked `@ExperimentalKtorApi`
and uses Kotlin context parameters. The untyped `install(Authentication)` / `authenticate("name")` API remains for
backward compatibility.

# Motivation

1. **Nullable principals in mandatory auth.** `call.principal<T>()` remains `T?` even inside authenticated routes,
   forcing defensive null checks everywhere.
2. **RBAC is not universal.** Many applications rely on claims or policy checks without a role model; a global roles API
   does not fit all use cases.
3. **Global role access is a footgun.** Role APIs should exist only when role-capable schemes are explicitly configured,
   not on every route.
4. **String coupling between providers and routes.** The provider name passed to `jwt("my-jwt")` and
   `authenticate("my-jwt")` is an unverified string — typos and type mismatches are caught only at runtime.

Opt in to `@ExperimentalKtorApi`. The DSL uses Kotlin context parameters.

# The Problem Today

### Nullable Principal in Mandatory Auth

Even inside an `authenticate { }` block the principal is nullable, forcing a defensive check on every route:

```kotlin
authenticate("my-jwt") {
    get("/profile") {
        val principal = call.principal<UserPrincipal>()
            ?: return@get call.respond(HttpStatusCode.Unauthorized)
        call.respond(principal.email)
    }
}
```

### Ad-hoc Role / Claim Authorization

Most projects implement custom route wrappers or inline checks against claims and principals. There is no typed
distinction between principal-only and role-capable flows, and nothing prevents accessing role APIs on routes where no
role resolution is configured.

### String-Coupled Provider Names

The link between the provider (`jwt("my-jwt") { ... }`) and the route guard (`authenticate("my-jwt") { ... }`)
is a plain string. A typo or a mismatch between the expected principal type and the actual one is only caught at
runtime.

# User Journey

## Step 1 — Define Your Principal

The principal type is any `P : Any`. Implementing `Principal` is not required.

```kotlin
data class JwtUserPrincipal(
    val userId: String,
    val email: String
)
```

## Step 2 — Create a Typed Scheme

Typed factories return a scheme. The `validate` block's return type is `P`. There is no separate
`install(Authentication)` step and no string-name wrapper:

```kotlin
val myJwt = jwt<JwtUserPrincipal>("my-jwt") {
    realm = "my-app"
    verifier(jwkProvider, issuer) {
        acceptLeeway(3)
    }
    validate { credential ->
        JwtUserPrincipal(
            userId = credential.payload.subject,
            email = credential.payload.getClaim("email").asString()
        )
    }
}
```

The same pattern applies to `basic`, `bearer`, `form`, `digest`, `session`, and `apiKey` in their respective modules.

## Step 3 — Protect Routes

Use `authenticateWith` instead of `authenticate`. Inside the block `call.principal` is non-null and typed to the
scheme's `P`:

```kotlin
routing {
    authenticateWith(myJwt) {
        get("/profile") {
            val user: JwtUserPrincipal = call.principal
            call.respond(user.email)
        }
    }
}
```

## Step 4 — Add Roles (Opt-in)

Define a role model and compose a role-capable scheme from the base scheme:

```kotlin
enum class Role : AuthenticationRole {
    User, Admin, Moderator
}

val roleBasedJwt = myJwt.withRoles { principal ->
    roleService.resolveRoles(principal.userId)
}
```

`roles` is an extension on the principal, available only inside a `RolesContext` — it does not exist on principal-only
routes:

```kotlin
routing {
    authenticateWith(roleBasedJwt, roles = setOf(Role.Admin)) {
        get("/admin") {
            val userRoles: Set<Role> = call.principal.roles
            call.respond(userRoles.map { it.name })
        }
    }
}
```

Pass `roles = null` to resolve roles without enforcing them. Authenticated callers that lack a required role receive
HTTP 403 by default.

## Step 5 — Add Anonymous Fallback (Opt-in)

When some routes should serve both authenticated and unauthenticated users, compose an anonymous-capable scheme.
Requests without credentials receive the fallback principal. Requests with invalid credentials still fail
authentication.

The returned scheme's principal type is a common supertype `CP` of the authenticated and anonymous types:

```kotlin
interface Identity

data class AuthenticatedUser(val userId: String) : Identity
data class GuestUser(val label: String = "guest") : Identity

val myAuth = jwt<AuthenticatedUser>("google-jwt") {
    verifier(jwkProvider, issuer)
    validate { credential -> AuthenticatedUser(credential.payload.subject) }
}.orAnonymous { GuestUser() }

routing {
    authenticateWith(myAuth) {
        get("/feedback") {
            when (val user = call.principal) {
                is AuthenticatedUser -> call.respond(user.userId)
                is GuestUser -> call.respond(user.label)
            }
        }
    }
}
```

## Step 6 — Optional Authentication

When a route should work with or without authentication, `call.principalOrNull` is nullable. Invalid credentials still
fail:

```kotlin
routing {
    authenticateWithOptional(myJwt) {
        get("/me") {
            val user = call.principalOrNull
            call.respond(user?.email ?: "anonymous")
        }
    }
}
```

## Step 7 — Multiple Schemes

A route can accept any of several schemes with `authenticateWithAnyOf`. The first scheme that authenticates the call
supplies `call.principal`. All schemes must produce principals assignable to a common type `P`.

Scheme-specific context (for example `call.session` on a session scheme) is **not** exposed inside
`authenticateWithAnyOf` — only `PrincipalContext` is available.

```kotlin
interface AppUser {
    val email: String
}

data class JwtUser(override val email: String, val sub: String) : AppUser
data class BearerUser(override val email: String) : AppUser

val jwtScheme = jwt<JwtUser>("my-jwt") {
    verifier(jwkProvider, issuer)
    validate { credential ->
        JwtUser(
            email = credential.payload.getClaim("email").asString(),
            sub = credential.payload.subject
        )
    }
}

val bearerScheme = bearer<BearerUser>("my-bearer") {
    validate { token -> BearerUser(email = lookupEmail(token)) }
}

routing {
    authenticateWithAnyOf<AppUser>(jwtScheme, bearerScheme) {
        get("/profile") {
            call.respond(call.principal.email)
        }
    }
}
```

## Step 8 — Map the Principal

`mapPrincipal` transforms a successfully resolved principal. If the original resolver returns `null`, the transform is
not invoked. If the transform returns `null`, the scheme rejects the call with HTTP 401.

```kotlin
data class AppUser(val id: String, val email: String)

val appJwt = myJwt.mapPrincipal { jwtUser ->
    userDirectory.find(jwtUser.userId)?.let { row ->
        AppUser(id = row.id, email = row.email)
    }
}

routing {
    authenticateWith(appJwt) {
        get("/me") {
            call.respond(call.principal.email)
        }
    }
}
```

## Step 9 — Error Handling

Set a default failure handler on the scheme or override it per route. Route-level `onUnauthorized` takes precedence
over the scheme-level handler, which takes precedence over the provider challenge.

For role-based routes, `onForbidden` is invoked when authentication succeeds but required roles are missing. Route-level
`onForbidden` overrides the handler passed to `withRoles`.

```kotlin
val myJwt = jwt<JwtUserPrincipal>("my-jwt") {
    verifier(jwkProvider, issuer)
    validate { credential -> /* ... */ }
    onUnauthorized = { cause ->
        call.respond(HttpStatusCode.Unauthorized, cause.toString())
    }
}

val roleBasedJwt = myJwt.withRoles(
    onForbidden = { call.respond(HttpStatusCode.Forbidden) }
) { principal ->
    roleService.resolveRoles(principal.userId)
}

routing {
    authenticateWith(
        roleBasedJwt,
        roles = setOf(Role.Admin),
        onUnauthorized = { call.respond(HttpStatusCode.Unauthorized) },
        onForbidden = { call.respond(HttpStatusCode.Forbidden) },
    ) {
        get("/admin") {
            call.respond(call.principal.email)
        }
    }
}
```

`authenticateWithAnyOf` takes a `MultiUnauthorizedHandler` that receives a map of the scheme name to
`AuthenticationFailedCause`. When omitted, the first scheme-level `onUnauthorized` is used, then default challenges.

# Rejected Alternatives

These were considered in earlier drafts of this KLIP and are **not** part of the implemented API.

**Wrap untyped providers.** A `createAuthScheme<P>("my-jwt")` helper would bind a principal type to an
existing `install(Authentication) { jwt("my-jwt") { ... } }` provider by name. That keeps string coupling between
configuration and routes. Typed factories return the scheme from the same call that builds the provider, so the name is
not re-entered.

**Separate `ktor-server-typesafe-auth` module.** Context-parameter route builders were planned for a companion module so
`ktor-server-auth` stayed unchanged. The implemented API lives in `ktor-server-auth`
(and provider modules such as `ktor-server-auth-jwt`) under `@ExperimentalKtorApi`.

**`authenticateWith(vararg schemes)`.** Multiple schemes on one route are `authenticateWithAnyOf`. Required
`authenticateWith` takes a single scheme so the route can also receive that scheme's extension context `C`.

**Role cache / `createRoleBasedAuthScheme`.** Role resolution is a `withRoles` callback on each request. There is no
`RolesCacheStrategy` and no factory that creates a role-based scheme from a provider name without a base scheme.

The API is `@ExperimentalKtorApi`. The signatures below omit that annotation.

## JWT factory

```kotlin
inline fun <reified P : Any> jwt(
    name: String,
    configure: TypedJwtAuthConfig<P>.() -> Unit
): SimpleAuthenticationScheme<P>
```

`TypedJwtAuthConfig` includes `realm`, `verifier(...)`, `validate { credential -> P? }`, and optional
`onUnauthorized`. Other typed factories (`basic`, `bearer`, `form`, `digest`, `session`, `apiKey`) follow the same
`name` + configure + `SimpleAuthenticationScheme<P>` (or session/OAuth-specific scheme) pattern.

# Technical Details

## Behavior

1. `authenticateWith` creates a child route and registers the scheme's named provider on first use. Reusing the same
   provider object reuses the registration. A different provider with the same name fails fast.
2. On each call the provider authenticates, then the scheme resolver produces `P`. Success stores `P` in a typed
   attribute used by `call.principal`.
3. For `orAnonymous`, missing credentials produce the fallback principal. Invalid credentials still fail.
4. Failure handling order: route-level `onUnauthorized`, then scheme-level `onUnauthorized`, then provider challenges.
   When none respond, authentication fails with `401 Unauthorized`.
5. For `authenticateWithOptional`, missing credentials skip failure handling and leave `principalOrNull`
   as `null`. Invalid credentials still invoke unauthorized handling.
6. For role-based overloads, roles are resolved after a successful principal. If `roles` is non-null and the resolved
   set does not contain every required role, `onForbidden` runs (HTTP 403 by default). Missing credentials on the
   optional role overload skip role checks.
7. `mapPrincipal` runs only after a non-null principal. A `null` transform result is
   `AuthenticationFailedCause.InvalidCredentials`. Exceptions from the transform propagate.
8. Nested `authenticateWith` layers are cumulative: each layer installs its own route-scoped plugin.
9. `authenticateWithAnyOf` tries schemes in declaration order against a shared `AuthenticationContext`. The first
   success wins. Only `PrincipalContext` is provided to the route block.
10. Legacy `authenticate("name")` / `install(Authentication)` continues to work and can nest with typed routes. Typed
    and untyped APIs coexist.

## Context parameters

Route builders pass `PrincipalContext` (or `OptionalPrincipalContext`), the scheme extension context `C`, and optionally
`RolesContext` as context parameters. Property access (`call.principal`, `principal.roles`)
resolves per call. Type safety comes from binding `P`, `R`, and `C` to the scheme: `roles` is inaccessible in a
principal-only block, and `principal` is typed to the scheme's `P`.

## Module ownership

- `ktor-server-auth` — `AuthenticationScheme`, route builders, composition (`withRoles`, `orAnonymous`,
  `mapPrincipal`), typed factories for basic, bearer, form, digest, and session, plus OAuth 2 helpers.
- `ktor-server-auth-jwt` — `jwt<P>(name) { ... }`.
- Untyped `Authentication` providers and `authenticate(vararg configurations)` remain in `ktor-server-auth`.

# Ktor-Defined vs. User-Defined

## Ktor-Defined

- Typed factories, scheme types, and route entrypoints
- Lazy named-provider registration and uniqueness
- Execution order and status semantics (401 unauthenticated, 403 role mismatch by default)
- Anonymous fallback when `orAnonymous` is used
- Optional unauthorized / forbidden handlers
- Role visibility only in `RolesContext`

## User-Defined

- Principal model (`P : Any`)
- Scheme names passed to typed factories
- Role model (`AuthenticationRole`) and `withRoles` resolution, if needed
- Anonymous principal factory via `orAnonymous`
- Principal mapping via `mapPrincipal`
- Route policies, required roles, and custom failure handlers

# Advantages

1. **Compile-time principal safety.** `call.principal` is non-null and correctly typed inside
   `authenticateWith` — no cast, no defensive `?: return` check.
2. **No global RBAC footguns.** `roles` is only available inside a `RolesContext`, preventing accidental role access on
   routes where no role resolution is configured.
3. **No string coupling.** The object returned by `jwt<P>(name)` is the same value passed to
   `authenticateWith`.
4. **Composable.** Role mapping, anonymous fallback, and principal mapping layer on a base scheme via
   `withRoles`, `orAnonymous`, and `mapPrincipal`.
5. **Lazy registration.** Schemes can be created as values and first used at the route; there is no required
   `install(Authentication)` block for the typed path.
6. **Backward compatible.** Untyped `authenticate` remains. Typed APIs are additive and experimental.

# Drawbacks

1. Larger public surface in `ktor-server-auth` (`AuthenticationScheme`, extra route overloads, handlers).
2. Role checks require wrapping schemes with `withRoles`.
3. `@ExperimentalKtorApi` until the design is frozen.
4. Context parameters require a compiler that supports them; the extra implicit receivers can be surprising in IDEs and
   when mixing typed and untyped routes.
5. `authenticateWithAnyOf` drops scheme-specific context, so session or OAuth helpers are not available inside that
   block.

# Future Directions

The following ideas are **not part of this proposal**. They illustrate possible extensions that stay consistent with the
patterns introduced above.

## 1. Policy / Attribute-Based Authorization

Unlike flat role enums, policies are structured values with parameters that support attribute-based decisions depending
on the request context.

```kotlin
sealed interface PolicyDecision {
    data object Allow : PolicyDecision
    data class Deny(val reason: String) : PolicyDecision
}

fun <P : Any, Policy : Any, C> AuthenticationScheme<P, C>.withPolicy(
    evaluate: suspend RoutingContext.(P, Policy) -> PolicyDecision
): PolicyBasedAuthenticationScheme<P, Policy, C>
```

Usage — the policy value is passed per-route instead of a role set:

```kotlin
data class OwnerOnly(val documentId: String)

val securedJwt = myJwt.withPolicy { principal, policy: OwnerOnly ->
    val doc = documentService.get(policy.documentId)
    if (doc.ownerId == principal.userId) PolicyDecision.Allow
    else PolicyDecision.Deny("Not the owner")
}

routing {
    authenticateWith(securedJwt, policy = OwnerOnly(documentId = "123")) {
        put("/documents/123") {
            call.respond(call.principal.email)
        }
    }
}
```

The same pattern works for external policy engines (OPA, Cedar) — the evaluator calls out to the engine inside
`withPolicy`.

## 2. Claim-Based Authorization Helpers

For cases where a full role model is unnecessary and gating on JWT claims or scopes is enough:

```kotlin
fun interface ClaimCheck<P : Any> {
    suspend fun check(principal: P): Boolean
}

infix fun <P : Any> ClaimCheck<P>.and(other: ClaimCheck<P>) = ClaimCheck<P> { principal ->
    this@and.check(principal) && other.check(principal)
}

infix fun <P : Any> ClaimCheck<P>.or(other: ClaimCheck<P>) = ClaimCheck<P> { principal ->
    this@or.check(principal) || other.check(principal)
}
```

Composable predicates can be applied inside `authenticateWith` without defining `AuthenticationRole` or
`withRoles`:

```kotlin
val emailVerified = ClaimCheck<JwtUserPrincipal> { it.emailVerified }
val hasReadScope = ClaimCheck<JwtUserPrincipal> { "read:documents" in it.scopes }

authenticateWith(myJwt, claims = emailVerified and hasReadScope) {
    get("/documents") {
        call.respond(call.principal.email)
    }
}
```
